Part two: re-pasted rows, exclusions, and rows picked by label.

So far, everything in this module was step one of the reproduction: raw snapshots to small tables. The paper has a second step too, from the authors' spreadsheet to the tables in the paper. The real project reproduces that step from the public version of the workbook. Two of the workbook's sheets are loaded into SQLite, and two more shared SQL files reduce them. R and Python both run those files unchanged. Before the SQL existed, the same work was done in R. In the exercise file these are blocks five to eight.

The first sheet is a yearly panel: one row per California billionaire per year, with worth and twenty-seven columns of income and taxes, all in millions. The second is a tax-statistics table: for each tax year, one row per income bracket, with the number of returns, income, taxable income, and tax, in dollars. Both tables keep one extra column, row num, the row's position in the sheet it came from. Hold on to that column. Block five needs it, and block eight is about not using it.

Block five keeps the rows that count. It is a chain of two C T Es. The first, called kept, drops the people on an exclusion table, with not in, followed by a subquery. That is the same pattern as block one's exclude list, and it carries the same warning: a single null id in the list would empty the result. The real loaders never write one.

The second C T E handles a data-entry accident. The real sheet has a block of four rows pasted twice at its tail. The fix is a window function from module five, row number. It is told to partition by year, forbes id, and worth, and to order by row num. Read that as: put the rows into groups that share the same year, the same person and the same worth, sort each group by its position in the sheet, and number the rows one, two, three. Then a where clause keeps copy number one. The first copy survives, every later copy goes. In R this was the duplicated function on those three columns, negated, which also keeps the first occurrence.

Why those three columns? Because they define what the same observation means. One of the pasted copies differs in a column outside the key, a re-typed dividend, and it still goes, which is right. And the key leaves alone two rows with the same person and year but a different worth. In the real data those are two separately tracked fortunes, and both count. The course data has one such pair, in 2022.

Two tempting shortcuts fail here, and the grader catches both. Select distinct, star, removes nothing, because row num is different on every row. And a self-join that looks for an earlier row with an equal worth misses one copy: the pasted row with no worth at all. Null equals null is not true, so the join finds no match. Partition by, like group by, puts all the nulls in one group, which is exactly what R's duplicated does with two missing values.

Does the order of the two filters matter? No. The groups include the forbes id, so an excluded person never shares a group with anyone else.

Block six sums the kept rows by year. Group by year, count star as n, and one line per money column: coalesce of the sum, with zero, divided by one thousand point zero. Three small things deserve attention. Count star, not a count of the worth column, because the row with no worth is still a person, and counting the column would come up one short in 2025. Coalesce, because in the course data one column is empty for every row of 2019, and a sum of nothing but nulls is null, while R's sum with n a dot r m equals true gives zero. And the point zero, because in SQLite an integer divided by an integer is integer division: seven divided by two is three. The point zero makes the division floating point, whatever type the column was loaded as.

Blocks seven and eight read the tax table. Block seven is a group by tax year with four sums and a count of brackets. It first keeps only rows where the tax year is not null, because the loaded table ends with a footnote row that has no year, and group by would otherwise give it a group of its own.

Block eight is the lesson of this part. It picks the rows of the top income brackets. The old R code did it by position: the top bracket of one year is a certain sheet row. That is correct for one version of the sheet and silently wrong for the next. Here the year blocks have different lengths. Up to 2020 the top bracket is five million dollars and over. From 2021 the source split it into five to ten million, and ten million and over. Add a year at the top of the sheet and every row below moves. The grader does exactly that: it runs your file a second time on a copy with a 2023 block added at the top.

So the SQL picks rows by what they are, not where they sit. A C T E first cleans the label with the replace function, turning every double space into a single space, because the sheet puts two spaces on each side of the small linking words in its labels, but not always. Then a case expression maps each cleaned label to a short key, and a where clause with an in list keeps only those three labels. Row num stays in the output, to sort and to trace each number back to its sheet row, but it never decides which rows are kept.

One detail about replace: it works through the text from left to right in pairs, so three spaces in a row would become two, not one. It is fine here because the sheet never has three.

That is part two. Keep the first copy with row number. Count rows with count star. Turn empty sums into zero with coalesce. And choose rows by a key or a label, never by their position.
